TDPHAnalyzer.Scan takes an explicit selected .dproj, .dpr, .dpk or .groupproj, configuration, platform, defines and external-root whitelist. Its root is the selected entrypoint's directory. It follows project members, explicit unit references, uses/contains/requires clauses, includes and resource directives; it never recursively inventories arbitrary source directories. Project unit/include/resource search paths and unit scopes are bounded to the root or explicit external roots. External files receive external/<whitelist index>/<relative path> identities. Reparse-point ancestors are excluded, and the opened file handle's resolved Windows path must match the requested absolute path before bytes are read. Missing dependencies, excluded paths and unprovided reference-path macros produce diagnostics. Missing files remain explicit manifest entries; exclusions are explicit diagnostic records.

MSBuild/XML handling is a passive, restricted evaluator, not a build. It reads supported property groups, item references and simple quoted/numeric comparisons with parentheses and AND/OR/NOT. Undefined MSBuild properties in conditions have empty values; unresolved reference-path macros do not collapse into guessed filenames. EXISTS and other unsupported expressions are unknown. XML DTDs/entities are rejected before XML parsing. Imports, targets, Exec, deployment hooks, scripts and analyzed binaries are never executed. Project-group member configurations are isolated. Shared source requested under different define sets is diagnosed as partial rather than represented as a complete multi-variant analysis. The caller initializes COM on its owning Windows thread before using the XML adapter; tests do so explicitly.

Acquisition and provenance
TDPHSource opens input read-only with sharing, captures original bytes and SHA-256, and records encoding/line-ending metadata. UTF-8 with or without BOM and UTF-16 LE/BE BOM are supported. Decoding must round-trip exact bytes. Invalid Unicode is not guessed as ANSI. An explicit legacy code page is accepted by the source API; the inventory currently quarantines such files until that setting is provided by a later configuration UI/API extension. Supplementary Unicode characters retain byte boundaries across the surrogate pair. Ranges are zero-based, end-exclusive original byte offsets; text line/column positions are one-based UTF-16 positions. Binary form line/column positions are unavailable (zero). Raw binary resources are fingerprinted and marked opaque.

No persistent full source snapshots are created. Original bytes, tokens and trivia live in memory during a scan. Persisted syntax evidence contains derived IR, declaration signatures, expressions, serialized form overrides and ranges, not full original files or the full raw token stream. Source metadata is stored as revision-linked evidence alongside the existing manifest/revision fields.

Syntax IR version 1, analyzer DPH-WP2-1
The lexer preserves whitespace, comments, strings, directives, exact byte ranges and line/column mappings. The preprocessor retains inactive and unknown tokens, expands bounded includes with per-file source mappings, and tracks known defines and tri-state conditional expressions. Unsupported compiler symbols/options stay unknown; a DEFINE/UNDEF inside an unknown branch makes subsequent decisions on that symbol unknown. Include cycles, unterminated literals/blocks, malformed numbers and depth limits are diagnosed.

Pascal IR is structural syntax, not a Delphi compiler or semantic type checker. It records units/programs/libraries/packages, references, type declarations, fields/properties, routine prototypes and implementations, overload signatures, nested/anonymous routines, expressions and common branch/loop/try/case statements. Some type expressions and signatures are retained as syntax spans rather than fully typed trees. Assembler and unsupported constructs become opaque nodes with diagnostics. Advanced generic specializations, attributes, variant records, class storage/property syntax and other compiler grammar remain incomplete. Errors may interrupt recovery of later declarations; no full-coverage claim is made for those files.

Significant/recognized/opaque token counts measure structural classification of the selected active variant, not semantic correctness or compiler acceptance. Diagnostics can mark a result partial even with zero opaque tokens. Unknown active-variant tokens count as opaque; inactive tokens remain available in memory. Nodes spanning include boundaries are not given a fabricated contiguous range across files: they are marked partial, and token source mappings remain authoritative.

Project XML IR records property/reference/import/target syntax facts and source ranges. Text DFM/FMX parsing records object/inherited/inline hierarchy, nested components, serialized properties, multiline text, sets/lists/collections and blob ranges. Binary TPF0 is decoded directly with bounded reads, without instantiating component classes. Binary floating-point payloads remain explicit encoded-float values; unsupported binary tags/encodings are partial. Base-form inheritance, runtime default values, component class semantics and event method resolution are not inferred. OnClick = btnConvertClick is a serialized event-name fact; confirmed semantic relationships belong to WP3. Other resources/configuration files are captured with an opaque-adapter diagnostic.

Bounds
16 MiB per captured file, 128 MiB captured project bytes, 10,000 acquired files, 64 project-reference levels, 32 include levels, 128 conditional/parser/form nesting levels, 250,000 tokens per expansion, 100,000 nodes per parser, 1 MiB serialized form property, and a Pascal/form budget checked at 500,000 aggregate token/node entries before parsing another file. Diagnostic Report limits each collection to 10,000 entries. Limits yield explicit partial/error results. These are conservative application limits, not a claim of comprehensive adversarial sandbox certification. Analysis results are private to their owning worker until staged; SQLite still has its single owning writer.

Incremental foundation
The analyzer caches parsed syntax in memory, keyed by analyzer version, selected root, external roots, file identity/hash, project/include hashes, defines, configuration and platform. All includes/project files conservatively invalidate dependent cache entries. Each scan rediscovers bounded inputs and rechecks hashes; reuse currently avoids Pascal/form parsing, not all acquisition/lexing. Cache bounds are 64 entries and 250,000 aggregate token/node entries, with conservative eviction. AIncremental=False bypasses reuse. Exact deterministic full/incremental JSON equivalence is tested before and after an include edit. Persistent cross-session parse caching and automatic file watching belong to later work.

Storage integration
TDPHScan.Stage observes the captured manifest and begins a generation using the caller's matching selected configuration ID. The caller must persist the same explicit configuration used for Scan; this headless API does not choose an IDE environment. It stages revision-linked source metadata, syntax IR evidence, syntax entities and diagnostics. Entity structural metadata accepts validated JSON through the backward-compatible AddSourceEntity optional parameter. AddDiagnostic writes generation-scoped diagnostics. SQLite schema remains version 2; no migration bytes were changed.

Syntax identities use source path, enclosing named syntax, declaration kind/name, routine signature and an occurrence discriminator. They survive whitespace/source-offset shifts. They are not WP3 semantic identities: renames, signature changes, duplicate/reordered declarations and cross-file moves still need later continuity/review logic. Entity analysis status and evidence stay partial/inferred for semantic interpretation even when a narrow syntax generation is complete. No call edges, CFG, confirmed event target, impact result or business rule is fabricated.

TDPHScan.Publish reacquires fingerprints and availability. A changed source supersedes the staged generation, observes the new fingerprints, sets modification/stale flags and requests reassessment while retaining the previous head. A stable but partial scan is retained as a partial generation and cannot replace a complete head. Revalidation does not mutate the original captured IR/diagnostics. The stored derived facts remain tied to captured file revisions. Live rescheduling/worker orchestration is deferred; RequestReassessment is the existing persistent request flag.
