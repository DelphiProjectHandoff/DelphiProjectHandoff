Implementation
DPH.Storage.Types contains manifest and status records. DPH.Storage.Database implements the core TDPHKnowledgeStore. These are storage-domain units, not UI helpers or Pascal class helpers. No controls, events, or design-time UI properties were changed. The application compiles these units but does not open databases on startup. Integration into the Explorer belongs to WP4.

One database belongs to one selected project/root. Open rejects a conflicting root; reviewed source relocation remains later work. Database and backup destinations must be outside the selected source root. Reparse-point ancestors are rejected so lexical path checks cannot silently accept a junction alias. This is a conservative boundary policy, not support for resolving arbitrary linked trees. Selected sources are never opened for writing by storage.

Schema
001_foundation.sql creates normalized project/configuration/generation/file/revision/manifest, entity/evidence/relationship, diagnostic, manual knowledge/review, audit and artifact-location records.
002_constraints.sql adds generation-bound property/CFG tables, translation/artifact/export metadata, indexes and history-protection triggers. These are empty persistence contracts for later packages, not implementations of graph generation, translation or publishing.
Additions to the logical blueprint: project_state separates the published-head pointer and flags; generation_files ties exact revisions to captured generations; artifact_blobs provides a nullable content-addressed artifact/snapshot location. Composite foreign keys enforce matching project and generation identities. Artifact paths and blob IDs are separate exclusive fields instead of an ambiguous path-or-ID field.
The migration runner splits only at the explicit '-- DPH STATEMENT' marker; trigger-body semicolons stay intact. Migrations are transactional, logged with SHA-256 and UTC timestamps, and reflected in PRAGMA user_version. Applied migration checksums cannot change. Git attributes pin migration files to LF for consistent byte checksums on checkout.
Existing databases receive a consistent pre-migration VACUUM INTO backup before an upgrade. New empty databases do not receive an intermediate backup. Failure rolls back the failing migration; preceding successful versions remain usable. Newer schema versions, missing/inconsistent ledgers and changed checksums are rejected.
SQLite is statically linked through FireDAC.Phys.SQLiteWrapper.Stat, measured version 3.42.0. Foreign keys and synchronous FULL are enabled. FTS5 capability is detected (present here); ordinary indexed lookups remain available. No full-text search service is implemented yet.

Manifest and generation API
Call InitializeProject, AddConfiguration, SelectConfiguration, then ObserveManifest with the complete current bounded manifest. Paths must be lowercase project-relative slash paths without dot/traversal segments, drive prefixes, duplicate paths or control characters. Available entries require a lowercase 64-digit SHA-256 and nonnegative byte length. Missing/excluded/unreadable entries require an empty hash. This validation does not discover paths or replace WP2's acquisition boundary checks.
ManifestHash sorts the entries and hashes deterministic JSON including path, hash, size, kind, encoding and availability. Omitted old entries remain in source_files as missing history but leave the active manifest. Only changed entries receive reassessment flags. Rename matching is not guessed or performed.
BeginGeneration captures the current configuration and manifest in a transaction. Available revisions are deduplicated by file/hash and linked into generation_files. There is at most one running generation. Stable logical entity keys are separate from generation-scoped versions; a move between files requires review. AddSourceEntity currently records a partial structural placeholder, not parsed semantics.
AddEvidence requires a captured file revision and a JSON byte range {"start":N,"end":N}. Database constraints reject invalid ranges and evidence from another generation. Relationships require source/target versions and evidence from their producing generation; unresolved targets may be null. Verification and certainty remain separate fields; storage does not verify program behavior.
PublishGeneration requires the caller's freshly revalidated complete manifest, a coverage-summary JSON object, and an explicit analysis-complete Boolean. It compares captured rows, captured fingerprint, current observed manifest, revalidated manifest and selected configuration. WP2 must actually acquire and recheck source bytes and call ObserveManifest; storage does not pretend to have independently checked live files. Full source-capture/publication scheduling and mid-scan source-change requeue belong to that coordinator.
Only coherent, caller-declared complete generations without missing/unreadable inputs can replace the published head and clear dirty/stale/error/manual-reassessment flags. Incomplete analyses become partial, retain the previous head, and leave stale state visible. Mismatches become superseded; explicit failures become failed. Terminal generations and their facts cannot be modified or deleted. 'Current' means coherent published storage input, not human verification or complete language support. Coverage summaries must remain visible to later UI/export consumers.
Publication never resolves human review tasks or overwrites manual knowledge revisions. This foundation conservatively marks all active manual records for review on a manifest change; source-specific impact narrowing belongs to later semantics/review work. Rejected/retired records remain rejected/retired.

Writer and readers
The creator thread owns the FireDAC writer connection; direct use from other threads is rejected. A named Windows mutex rejects another DPH writer for the same canonical database path. QueueWrite accepts a bounded (256 command) in-memory queue; ProcessQueuedWrites executes accepted callbacks on the owner thread. Queue-full and callback errors are reported as exceptions, not successful writes. Queued callbacks are not durable until executed/committed; process crashes may lose unexecuted commands. Producers must stop/join before destroying the store; graceful destruction shuts down and drains accepted commands on the owner thread. Worker lifetime and application scheduling remain coordinator responsibilities.
Connections use LockingMode=Normal, SharedCache=False, a 3,000 ms busy timeout and LockWait=True. Busy writes fail safely after the timeout and may be retried after the competing lock is released. WAL is explicit opt-in and rejected for UNC database paths; deployment suitability is not inferred for arbitrary network/shared drives. The default is rollback-journal mode.
Independent readers should use ReadOnly, LockingMode=Normal, SharedCache=False, and the same journal mode; use a transaction to hold a generation-consistent snapshot. With local WAL, the test confirms an old reader snapshot remains stable while the writer publishes, and a new transaction sees the new head.
FireDAC parameter reference used during implementation: https://docwiki.embarcadero.com/RADStudio/Florence/en/Connect_to_SQLite_database_(FireDAC)

Recovery and backup
At open, a sole writer marks abandoned running generations failed with INTERRUPTED diagnostics, retaining the previous head and curated records. Atomic publication has SQL-fault and hard-process-termination tests. The hard-crash fixture terminates a separate DPH test process during an uncommitted SQLite publication-shaped transaction; it does not terminate the IDE or any user application. It verifies SQLite rollback plus the production store's startup recovery, not power-loss durability on every storage device.
BackupTo uses SQLite VACUUM INTO for a consistent committed database image rather than copying a live database file. It refuses an existing destination or one inside selected source. IntegrityCheck includes SQLite integrity and foreign-key checks. Tests restore a current backup and inspect a pre-upgrade version-1 backup with manual notes. Optional source snapshots, packaging and user retention policies remain unimplemented pending their configuration decisions.
