Learn a Delphi application, follow its evidence, and preserve what its author knows.

Find your way around the window

DPH opens maximized to fill the available Windows desktop. The Selection details pane is on the right. Double-click an object in the far-left object list to fill this pane with its name, kind, signature, source location, generation and evidence hash. Click the Explain tab in the centre for its behavior, callers and effects. Click Source for its code.

The details text wraps to fit its pane; scroll down inside it to read more. Drag the vertical divider just to its left to change its width. If you restore the window to a smaller size, use the horizontal scrollbar directly below the top command buttons to reach commands that do not fit.

A small learning exercise

Choose one button that interests you. Write down the expected result before reading its code. Follow its event to the handler and answer:

  1. Which inputs does the handler read? Where are they checked?
  2. Which conditions can stop or change the operation?
  3. Which routine does the actual work? Is it called directly or supplied as a callback?
  4. Which data or visible state might change? What would demonstrate success?
  5. Which fact is still unresolved, inferred or missing a business explanation?

Create a linked Knowledge record for the missing answer, give it a clear title and named author, and leave it pending review until someone checks it. Do not turn your expectation into a verified fact merely because a name sounds plausible.

Delphi terms, in plain language

Unit
A Pascal source module containing declarations and implementations.
Class and component
A class defines data and operations. A form component is an instance declared in the interface design, such as a button or edit box.
Procedure, function and signature
A procedure performs an operation; a function also declares a return value. The signature describes its parameter and result types.
Event and handler
An event property connects an interaction to a routine. That routine is its handler. A static binding establishes the declaration, not proof that a user triggered it.
Branch and loop
A branch chooses a path according to a condition. A loop may repeat. A control-flow graph (CFG) shows the captured possible paths.
Callback and asynchronous work
A callback is code supplied for another operation to invoke. Background or queued work may run later or on another thread; a static trace cannot prove its timing.
Read, write and side effect
A read uses a value; a write may change it. A side effect changes something beyond returning a result, such as an object, file or display.
Generation, fingerprint and certainty
A generation captures one source/configuration revision. Its fingerprint identifies that capture. Confirmed static, inferred, possible dynamic and unresolved describe how a relationship was established.

Run a repeatable check

  1. Attach a small project with known handlers. Confirm its startup statements and follow one event into Explain.
  2. Compare a branch, callback and output with Source. Check the certainty labels and coverage gaps.
  3. Save a named Knowledge note, close DPH, and reopen its cache. Confirm the note and historical generation remain available.
  4. Publish to a new folder outside source. Open its index.html and the selected object's explanation. Validate the bundle with DPH.ValidateHandoff.exe <bundle> <trusted fingerprint>. Use --allow-stale only to inspect explicitly historical/partial bundles.
  5. Use the User Guide's maintenance exercise for a separately authorized source change and reassessment.

Inspect stored procedures functions and triggers

Open the intended project or cache and choose Database schema in the upper-right page selector. A procedure groups database work, a function declares a returned value and a trigger associates work with a database event. The details memo begins with the stored-object name, captured CREATE operation, language, return type and ordered parameters. Each parameter shows position, exact name, IN/OUT/INOUT or supported output mode, declared type, default text and source line. Literal default values are replaced with a literal-omitted marker. Not declared means absent from the captured statement, not an engine default or proof that a value cannot be returned.

For a trigger, read Trigger table, Timing, Events, Scope and WHEN before the body. BEFORE, AFTER and INSTEAD OF describe captured timing; they are not observations of an execution. A supported trigger can retain an inline block or an explicit zero-argument function call. WHEN remains unevaluated text. Unsupported event or option grammar stays in an explained gap.

Define table and column business meanings

A data dictionary explains what a table or column means to the people using the application. DPH captures technical SQL structure, but a knowledgeable contributor must supply business meanings. Open Database schema in the upper-right page selector. Select a declared table or column. The labeled details area starts with its saved business dictionary, or explains that none has been recorded for these captured source bytes.

Scroll the command strip horizontally to the right and click Edit dictionary. Enter the named contributor, Business definition, Business owner or steward, Sensitivity and handling, and Evidence and remaining unknowns. These fields are required; explicitly write Unknown and the person or evidence needed when an answer is unavailable. Units values and business usage is optional. Do not paste actual customer records, credentials or confidential example values. A sensitivity entry is documentation, not automatic access control.

The editor begins with business fields. Scroll downward to inspect the read-only schema identity, source path, SHA256, original capture generation, object kind/name, owning table and statement line. These identify the exact captured declaration; duplicate table names are not merged. DPH does not infer a business definition, responsible owner or sensitivity from an SQL name or declared type.

Click Apply to Knowledge draft. The editor closes and Knowledge displays the protected structured draft. Click Save to create an immutable revision. Apply alone does not persist anything. Use Discard edit if you do not want the draft. To change a saved definition, return to Database schema, select the same table or column and click Edit dictionary again. Editing requires a fresh human review.

Click Open dictionary history beside Edit dictionary to view contributor, editor, review state and immutable revisions in Knowledge. Enter the named reviewer and choose Verify review, Reject or Retire as appropriate. Saving a definition does not verify its truth. Additional canonical source, relationship, screenshot or section evidence can be added on Knowledge links. Open source on Database schema follows the selected captured source under the existing hash checks.

The Database schema text filter also searches saved current definitions, owners, sensitivity and usage. Clear the filter to restore the inventory. Tables or columns not captured as supported declarations cannot be given invented schema identities. A changed SQL resource does not automatically inherit its old dictionary. When the same source/record/name has historical text, details explains the mismatch and Open dictionary history preserves access. Other unmatched records remain in Knowledge. Recheck business facts and author a definition for the newly captured declaration.

Project handoffs include matching attributed dictionary records through the existing Knowledge sections and structured canonical records. Source exclusions and selected source scope apply; definitions whose captured source hashes differ are omitted. Review business descriptions before publishing. Native controls remain editable in the Delphi IDE. No SQL, target application or database server is run by this workflow.

Inspect database read and write operations

Choose Database connections in the upper-right page selector, then choose database operation in its kind filter. Clear the text filter to see all captured requests; enter Post, Delete, read, insert or a calling routine name to narrow the list. Select a row. The evidence memo begins with its operation kind, requested effect and evidence basis. Operation requests are source candidates; DPH does not run the selected application or connect to its database.

Open, Refresh, navigation and search methods are read candidates. Append and Insert prepare a new record buffer; Edit prepares an update. AppendRecord and InsertRecord request insertion. Post submits a pending insert or edit, depending on the dataset state; cached updates can defer persistence. Delete requests deletion of the current record. ApplyUpdates can submit mixed pending writes. Cancel and CancelUpdates concern pending edits or cached changes. None of these calls proves transaction commit or rollback.

Literal SELECT, INSERT, UPDATE and DELETE text is classified separately from calls. Configuring SQL does not execute it. Joined statements retain their lexical family even when table and column binding is unsupported. Dynamic SQL, mixed batches and unsupported prefixes remain unknown. SQL values are omitted from this inventory. Inspect approved source locally to understand parameters and context.

Select Target via DataSet in the reference selector and click Follow reference to inspect the exact captured receiver. A dataset lists reverse operation references in the same selector. Click Source to open the original location only after attaching unchanged source; detached, changed and historical evidence refuses navigation. Use the horizontal toolbar scrollbar to reach Follow reference and Source when they are outside the visible area. Scroll within the evidence memo for engine evidence and unknowns. Full reassessment upgrades an older capture to the new analyzer. Explicit run and test directions are in docs/guides/Database_Operations_Run_and_Test.txt.

Follow dataset and screen field bindings
