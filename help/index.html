Welcome to Delphi Project Handoff

Learn a Delphi application, follow its evidence, and preserve what its author knows.

Your first ten minutes

You do not need to understand the whole symbol index before beginning. Start with a visible action and follow one path through the program.

  1. Select the analysis environment. In the header, choose the intended Debug/Release and Win32/Win64 configuration. Enter required extra compiler defines, separated by semicolons. For the pinned converter example use MSWINDOWS;WIN32.
  2. Choose Attach project. Select the application you want to document using its .dproj, .dpr or .groupproj. DPH rejects its own project and caches of itself. Save the proposed .dphdb database in the default Databases folder under the Handoff application folder, or browse to another location outside the selected source folder. Existing databases are not moved. DPH reads the program; it does not compile or run it.
  3. Wait for the captured generation. Read the status line along the bottom edge of the DPH window. To read the gaps, click the Learn the project tab in the centre, then click Coverage and troubleshooting in the topic list on the left side of that tab. PARTIAL means some behavior could not be established. An explanation does not remove those gaps.
  4. Open Learn the project → How the program starts. Read the captured startup statements. Look for initialization, form creation and the event loop where present.
  5. Open Screens and user actions. Choose a familiar button or other control. Follow its event binding, such as OnClick, to the handler.
  6. Read Explain. Identify what calls the handler, what it calls or changes, the decisions it makes and any background callbacks. Expand an evidence section to inspect its source location and rule.
  7. Open Source and Graphs. Compare the explanation with exact code and the procedure CFG. Then record an author answer in Knowledge for anything the source does not explain.
Already have a knowledge database? Click Open cache at the top. The picker starts in Databases; browse to your existing file if it is elsewhere. Keep its adjacent .dphdb.views folder with it. Rejected project or cache selections leave the current workspace intact. A detached cache is historical evidence; attach the source before approving current-source reviews.

Find your way around the window

DPH opens maximized to fill the available Windows desktop. The Selection details pane is on the right. Double-click an object in the far-left object list to fill this pane with its name, kind, signature, source location, generation and evidence hash. Click the Explain tab in the centre for its behavior, callers and effects. Click Source for its code.

The details text wraps to fit its pane; scroll down inside it to read more. Drag the vertical divider just to its left to change its width. If you restore the window to a smaller size, use the horizontal scrollbar directly below the top command buttons to reach commands that do not fit.

A small learning exercise

Choose one button that interests you. Write down the expected result before reading its code. Follow its event to the handler and answer:

  1. Which inputs does the handler read? Where are they checked?
  2. Which conditions can stop or change the operation?
  3. Which routine does the actual work? Is it called directly or supplied as a callback?
  4. Which data or visible state might change? What would demonstrate success?
  5. Which fact is still unresolved, inferred or missing a business explanation?

Create a linked Knowledge record for the missing answer, give it a clear title and named author, and leave it pending review until someone checks it. Do not turn your expectation into a verified fact merely because a name sounds plausible.

Delphi terms, in plain language

Unit
A Pascal source module containing declarations and implementations.
Class and component
A class defines data and operations. A form component is an instance declared in the interface design, such as a button or edit box.
Procedure, function and signature
A procedure performs an operation; a function also declares a return value. The signature describes its parameter and result types.
Event and handler
An event property connects an interaction to a routine. That routine is its handler. A static binding establishes the declaration, not proof that a user triggered it.
Branch and loop
A branch chooses a path according to a condition. A loop may repeat. A control-flow graph (CFG) shows the captured possible paths.
Callback and asynchronous work
A callback is code supplied for another operation to invoke. Background or queued work may run later or on another thread; a static trace cannot prove its timing.
Read, write and side effect
A read uses a value; a write may change it. A side effect changes something beyond returning a result, such as an object, file or display.
Generation, fingerprint and certainty
A generation captures one source/configuration revision. Its fingerprint identifies that capture. Confirmed static, inferred, possible dynamic and unresolved describe how a relationship was established.

Run a repeatable check

  1. Attach a small project with known handlers. Confirm its startup statements and follow one event into Explain.
  2. Compare a branch, callback and output with Source. Check the certainty labels and coverage gaps.
  3. Save a named Knowledge note, close DPH, and reopen its cache. Confirm the note and historical generation remain available.
  4. Publish to a new folder outside source. Open its index.html and the selected object's explanation. Validate the bundle with DPH.ValidateHandoff.exe <bundle> <trusted fingerprint>. Use --allow-stale only to inspect explicitly historical/partial bundles.
  5. Use the User Guide's maintenance exercise for a separately authorized source change and reassessment.

The full User and Engineering Guides are provided as editable DOCX files in docs/guides and companion PDFs in docs/pdf. Developers can run the scripts in tools; build-learning.cmd exercises the new learning interface and real WebView2 rendering.

Inspect component dependencies

Open a project and choose Component dependencies at the upper right. Select a component to read class-source candidates, unresolved or ambiguous declarations, source fingerprints and generation. All captured classes are listed; third-party origin cannot be established by a name alone. Explain class follows a unique inferred candidate. Component source requires attached unchanged text.

Click Edit dependency. Enter a named contributor and evidence, plus any known unit, package/product, vendor, version/configuration and support/replacement information. Blank optional fields remain unknown. Scroll the editor vertically. Click Apply to Knowledge draft, then Save on Knowledge. Apply alone does not save. Open in Knowledge shows history; add exact evidence links and save, then review explicitly with a named reviewer. Edits reopen review. Duplicate class identities are rejected ignoring case, including retired identities.

Filter by component, resolution, vendor or support. Next page advances through 250 rows and First page resets. Scroll the command bar horizontally at narrow widths; resize or scroll the details. Package declarations and unavailable inputs are project-wide context, not proof of membership or installation. Authored metadata never resolves missing source. Attach approved missing source roots and reassess. No vendor class, package or DLL is loaded.

Explicit steps: docs/guides/Component_Dependencies_Run_and_Test.txt. Developers run tools/build-component-dependencies.cmd elevated.

Inspect responsive layout rules

Open a project and choose Layout rules in the upper-right page selector. Select a component to read captured Align, Anchors, geometry, serialized parent, margins, padding, constraints, autosizing, wrapping, DPI and resize events with source evidence.

Scroll the command bar horizontally to reach Parent width change, Parent height change and Apply example. Enter positive or negative whole numbers from -10000 to 10000 and apply. Invalid input preserves the previous valid example. Applying refreshes the filter and returns to the first page. Numeric examples require explicit Align=None and recognized anchors on an ordinary child with a captured parent. Active alignment, inheritance and missing or unknown rules remain qualified.

Filter by component or explanation. Next page advances through 250 components; First page resets. Drag the divider and scroll the detail box. Component source requires attached unchanged text; detached, changed and binary locations are refused. Examples show basic changes, not absolute final geometry. Constraints, sibling allocation, defaults, custom code and DPI can alter actual behavior. Compare Object Inspector settings and resize the target separately.

Full steps: docs/guides/Layout_Rules_Run_and_Test.txt. Developers: run tools/build-layout-rules.cmd elevated for 56 focused checks.

Inspect dynamic controls

Open a project, attach its source and click Full reassessment for an older capture. Choose Dynamic controls at the upper right. Select a creation site to read source evidence and separate owner, parent, event and property references. Owner means lifetime ownership; Parent means visual containment. Runtime instance counts remain unknown.

Filter by routine, class, owner or event. Next page advances through 250 sites; First page resets. Scroll the command bar horizontally to reach Explain creation site, the relationship dropdown and Explain reference. Select a relationship before opening its declaration. Unresolved and nil targets disable reference Explain. Use Source from Explain for verified attached code.

Reused or overwritten handles and assignments before construction remain ambiguous. Aliases, factories, indirect handles and cross-routine changes may be unsupported. Full directions: docs/guides/Dynamic_Controls_Run_and_Test.txt. Developers: run tools/build-dynamic-controls.cmd elevated.

Inspect menus and commands

Open a project and choose Menus and commands at the upper right. Select a command to read its menu path, caption, action, shortcut codes, flags, source evidence and diagnostics. Filter by command kind or text. Next page advances through 250 rows; First page resets.

Scroll the command bar horizontally to reach Command source, Action source, the handler selector and Explain handler. Select the specific click, execute, update or popup binding before explaining it. Unresolved bindings disable Explain. Source commands require attached, unchanged text; detached, changed and binary locations are refused explicitly.

Paths follow serialized parents. Runtime order, dispatch precedence and state remain unobserved; missing properties remain unknown. Readable shortcut labels and possible conflicts are on Keyboard and focus. Full directions: docs/guides/Menus_and_Commands_Run_and_Test.txt. Developers: run tools/build-commands.cmd elevated.

Inspect keyboard shortcuts and focus order

Open a project, then choose Keyboard and focus in the upper-right page selector. Select a component to read its captured TabOrder, focus flags, shortcuts, action references, keyboard events, source locations and diagnostics. Common Windows shortcuts show readable names such as Ctrl+S.

Rows group by form and parent. A question mark means unknown or not applicable. Duplicate sibling positions and possible shortcut conflicts are review candidates. Runtime traversal remains unobserved. Missing defaults and inherited or external actions are not guessed.

Filter by component, property or diagnostic. Next page advances through 250-row pages; First page resets. Component source and Action source require attached, unchanged text evidence. Binary forms retain byte locations. Scroll the toolbar horizontally at narrow widths and scroll the detail box for explanations.

Full steps: docs/guides/Keyboard_and_Focus_Run_and_Test.txt. Developers: run tools/build-keyboard.cmd from an elevated Command Prompt.

Define the application business language

  1. Open the intended project and choose Business glossary in the upper-right page selector. Click New term.
  2. Enter the term, one optional alias per line, a plain-language definition, optional examples, relevance/evidence context and a named contributor. Context should identify why the term matters to this project and where its meaning came from.
  3. Click Apply to Knowledge draft, then Save on Knowledge. Applying alone does not save. Wait for the activity line to finish.
  4. Select the saved term on Business glossary and click Open in Knowledge to read immutable history. On Knowledge links, choose a target kind, enter a filter, click Find targets, select a source target/role and click Add link. Return to Knowledge and Save.
  5. Review the definition and exact current-source links, enter a named reviewer and click Verify review. A source change can reopen review.
  6. Use Edit term for changes, then Apply and Save. Rename keeps the stable identity. Duplicate terms/aliases are rejected ignoring case and repeated spaces; retired names stay reserved. Save or discard the existing draft before replacing it.
  7. Find names, aliases, definitions and examples with the glossary filter. In a narrow window scroll the command bar horizontally to reach it. Drag the divider below the term list to resize it, and scroll inside long definitions.
  8. Publish to a new folder outside selected source. The HTML Business glossary, both editable manuals, canonical.json and indexes/glossary.jsonl use the same term revision. Run Validate bundle and inspect review states before relying on business claims.

Explicit run and test steps are in docs/guides/Business_Glossary_Run_and_Test.txt. Developers can run tools/build-glossary.cmd from an elevated prompt. All term controls are editable in the RAD Studio form designer.

Translate saved knowledge offline

Choose Translations in the upper-right page selector after selecting a saved Knowledge revision. Enter the source and target locales and select an explicitly supplied DAT language pack. Compare the labeled source and localized text. Missing phrases remain source fallbacks; code, SQL, paths and hashes stay protected. Resolve the source section's review tasks before approving complete wording with a named translation reviewer.

The French sample at samples/translation/DPH.fr.sample.json translates the exact body Run conversion to Exécuter la conversion. It contains only three unreviewed phrases. It is not a complete language catalog.

Share and validate a handoff

  1. Choose Publish. Review scope, audience and exclusions. Leave Localized prose locale blank for normal publication, or enter the exact locale used for reviewed translations. Reviewed authored bodies appear in HTML and Localized_Sections.docx; other entries retain labeled source fallbacks. Titles, generated guidance and technical indexes remain in their source language.
  2. Include redacted source browsing pages is unchecked by default. Check it only when sharing captured code is intended. Original bytes are not copied; task bundles include cited line excerpts and mark omissions. Review output before sharing.
  3. Export to a new folder outside selected source. Open index.html and inspect the explanations, counts, provenance and omissions.
  4. Choose Validate bundle. Paste the trusted capture fingerprint, or click Use opened capture fingerprint after opening its trusted database. Select the exported root manifest.json and read the complete background report.
  5. Historical/partial inspection must be explicitly selected. An integrity pass does not prove current source, complete analysis, author identity or reviewed business procedures.

Inspect the selected project catalog and profile

Choose Projects in the upper-right page selector, then Selected project. Select a captured project/group file or program, library or package declaration. The memo below shows settings, references, generation, source hash and source lines. Missing referenced projects stay visible. Settings and main-source declarations can describe the same application. These rows do not verify built outputs or service installations.

Click Known databases to return to saved database locations. Click Project profile to record the contributor, purpose, ownership, environment and architecture. Purpose and attribution are required. Click Apply to Knowledge draft, inspect the generated text, then click Save on Knowledge. Applying alone does not save; owner-supplied statements still require review.

Inspect quality candidates and revision changes

Choose Source quality, select a category, optionally enter a filter and click Filter. Select a result to read its evidence and limits. Missing references, duplicate bodies, disconnected statements and call cycles are candidates for investigation. They do not establish that code is safe to delete. Open explanation follows the routine; Next 250 advances results.

To compare retained captures, choose Database tools and click Preview retention. Note an earlier generation ID with a retained cache. Choose Revision comparison, enter that ID in Before: saved generation ID, then click Compare. After is the currently displayed capture. Select a result to read the labeled Before and After panes; Next 200 advances results. Both captures must have matching analysis selections and analyzer contracts. This compares captured structure and fingerprints, not reconstructed historical source text.

Current limits and sharing

The rework is experimental. Supported source facts do not establish undocumented business policy, successful runtime operation or complete user procedures. Resource interpretation, semantic reuse and retention/rename review now have implemented controls with explicit bounds. Read docs/Implementation_Completion_Tracker.txt for current item-level evidence; docs/Rework_Requirements_Audit.txt records the historical gaps that prompted the work.

Review exported material and screenshots for private information. External AI, runtime instrumentation and online translation are disabled. DAT language-pack translation runs offline. This help makes no external requests.
