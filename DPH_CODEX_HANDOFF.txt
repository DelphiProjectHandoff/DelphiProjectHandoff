## 1. Product charter and non-negotiable boundaries

**Delphi Project Handoff (DPH)** is a standalone Delphi FMX application that thoroughly documents and explains **the specifically selected Delphi program**: source, forms, controls, logic, configuration, dependencies, outputs, tests, build, maintenance, user operation, and AI agent context. The goal is to enable a new programmer (“Mr. A”) to inherit and maintain a complex business-critical Delphi application using a reliable, deeply linked engineering and user reference.

- **Project-centric**: one explicitly selected Delphi `.dproj`/`.dpr` or project group per DPH knowledge store. Do **not** drift into unrelated company systems, generic corporate knowledge management, or unreferenced repos.
- **Independence**: VCL2FMXConverter is a separate product. **Never change its repo**, use it as a build/runtime dependency, establish a shared evolving library, or merge the projects. Its useful code may be copied and adapted after license/provenance review.
- **Read-only discovery**: do not change input project source, compile/execute input code, load untrusted packages, launch scripts, connect to production services, or capture runtime information as part of passive scanning. Special runtime instrumentation requires distinct explicit authorization.
- **Evidence before claims**: link every technical assertion to source/configuration/test/runtime evidence, or label it attributed human knowledge / unverified inference. No invented semantic edges or false claims of analysis completeness.
- **One authoritative knowledge store per project**, derived documentation outputs. Automatic incremental reassessment is the approved default.
- **Privacy and confidentiality**: no credentials, tokens, cryptographic secrets, unapproved source transfer, or external translation/AI calls without consent and safeguards.

## 3. Approved system design

### 3.1 Main technical pipeline
```
Selected Delphi project
  -> boundary/manifest and fingerprints
  -> read-only input snapshot, decoding, lexing and preprocessing
  -> Pascal + FMX/DFM + project-file parsing
  -> symbol resolution and typed dependency/event/call graph
  -> control-flow and selective data/side-effect analysis
  -> evidence, uncertainty and coverage classification
  -> revision-consistent transaction into SQLite
  -> Explorer/Inspector, diagrams, HTML manuals and agent bundles
```

All stages expose versioned, testable contracts and diagnostics. Prefer explicit intermediate representations and headless analyzers rather than coupling parsing directly to FMX.

### 3.2 Persistence
- **SQLite via Delphi FireDAC**, one `.dphdb` per selected project, stored outside the analyzed source tree by default.
- Persist normalized project/file/symbol/form/control/relationship/fact/evidence/knowledge/review/export metadata; source hashes, revision/generation IDs and analyzer versions.
- Separate automatically derived facts from manually curated knowledge. Rescanning must never destroy manually authored notes or history.
- Maintain distinct **modification detected**, **analysis stale**, **knowledge review needed**, **analysis failed**, and **manual reassessment requested** states rather than relying on a single Boolean.
- Open the cached project immediately, verify fingerprints in background, and analyze only changed elements plus impacted relationships. A full rescan is user-invokable.
- Commit a new coherent generation **atomically** only when its input fingerprints are valid; preserve the previous completed generation during failures, cancellation, or mid-scan source changes.
- Support connected/detached mode, relocatable project-relative identifiers, optional approved source snapshots, retention, integrity checks, and disaster-safe migrations.
- SQLite relational/indexed graph model; avoid a separate graph server unless formally approved.

### 3.3 FMX application and Explorer
- Three resizable panes: hierarchical Explorer, tabbed central workspace, context-sensitive Inspector. Persistent active-project identity and stale/review status.
- Drill down from project → unit/form → class/control → method/event → statement/property → evidence and related objects.
- Canonical entities have multiple navigation routes, including forward/reverse references, history, search, bookmarks, breadcrumbs, and object-level actions.
- Screen viewer modes: thumbnail gallery, fit, native size, zoom/full-screen and component inspection. **Distinguish design-time reconstruction from actual runtime screenshots.**
- Graph types: whole-program execution, procedure CFG, caller/callee, form navigation, data flow, change impact. Collapse large graphs; show uncertain edges visually.
- HTML panels may be hosted in FMX. Ensure embedded content is sanitized and restricted to authorized local project data.

### 3.4 Documentation and AI
- One canonical documentation/knowledge model generates engineering guide, user manual, maintenance, build/deploy, troubleshooting, orientation, contextual help, and AI handoff.
- HTML-first, offline-capable exports with internal linking/search, responsive views, print and optional PDF. Revisions and evidence carried through all views.
- Atlas translation via an **adapter**, with actual provider/API, transport, licensing and confidentiality reviewed before connecting. Translate prose, not code identifiers/paths/SQL/protocol keys. Cache by content/revision/locale; review translations.
- AI bundles: project manifest, exact source/configuration hashes, `AGENTS.md` **inside a generated agent handoff bundle only when explicitly requested** (never touch the owner's project-wide file), technical narrative, source indexes, typed relationship JSONL, evidence references, build/test/run constraints, known unknowns, coverage and validation checksums.
- Provide full and task-scoped technical bundles. Label unverified AI explanations and invalidate stale bundles.
